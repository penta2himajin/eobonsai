# eobonsai

## Overview

An inference setup tuned for one pairing: **Bonsai 2 27B** (PrismML ternary GGUF, derived
from Qwen3.8-27B) on a single **RTX 3060 12 GB** (GA106, `sm_86`, Ampere), for single-user
interactive chat and agent work.

The work is measurement-driven. This card has 64 INT32 lanes per SM, so its int8 `dp4a`
rate is only ~2.2x FP32 rather than the 4x a datacenter part gives, and it has 28 SMs with
a 3 MB L2. Those properties, not general advice, decide which optimizations are worth
attempting. The measured ceilings live in @docs/roofline-rtx3060.md and every performance
claim must be traceable to a file under `results/`.

Two constraints shape everything: the model only runs on the PrismML llama.cpp fork
(stock llama.cpp rejects the packings), and only ~11.5 GB of VRAM is free on this machine
because a display is attached to the card, so the 262K context budget is a real design
problem rather than a footnote.

## Project Structure

```
scripts/     entry points: setup, build, bench, roofline, ncu profiling
tools/       gguf-inspect.py (GGUF header reader), microbench/ (CUDA roofline kernel)
docs/        roofline-rtx3060.md, decisions/ (ADRs), protocols inherited from the template
results/     raw logs and CSVs from every run; tracked, because this is the evidence
config/      confirmed launch profiles (generated once measured)
third_party/ pinned llama.cpp fork checkout; NOT tracked, regenerated by scripts/build.sh
bin/ models/ out/ build/   downloaded or generated artifacts; NOT tracked
```

Source of truth by question: *how fast can this card go* -> `docs/roofline-rtx3060.md`;
*why was this chosen* -> `docs/decisions/`; *what actually happened* -> `results/`.

## Development Setup

Toolchain is pinned: CUDA 12.4 at `/usr/local/cuda-12.4`, `sm_86` only, fork commit
`adfffbe41b2cabcd51fff326ab045662265062bb`. `scripts/build.sh` clones/checks out that
commit itself; there is nothing to install beyond the CUDA toolkit and cmake/gcc/ninja.

```bash
# Pinned CUDA binary + both GGUF packs (~13 GB). Resumable and hash-checked.
scripts/setup.sh all

# Source build for kernel work. Pins sm_86 and the fork commit.
scripts/build.sh

# Pre-push hook (format / lint / clippy).
cp git-hooks/pre-push .git/hooks/pre-push && chmod +x .git/hooks/pre-push
```

Hardware counters require root on this machine (`RmProfilingAdminOnly = 1`), so profiling
runs as `sudo scripts/profile-ncu.sh`. `ncu` is already installed at
`/usr/local/cuda-12.4/bin/ncu`.

## Build & Test

There is no unit-test suite; verification here means measuring and reproducing. These run
without prior setup beyond `scripts/setup.sh all`:

```bash
scripts/roofline.sh                  # card ceilings; must reproduce docs/roofline-rtx3060.md
scripts/bench.sh bin/cuda PQ2_0      # baseline or A/B; writes results/bench-*.log
scripts/build.sh                     # sm_86 source build; needed before any kernel work
```

A change is verified only when its A/B result is committed under `results/` and the number
is quoted in the accompanying ADR or docs update. When the source build is in use, the
comparison must be source-build against source-build, not against the pinned prebuilt.

## Development Principles

- **Label the provenance of every number.** A figure measured on this machine is cited as
  `results/<file>`; a figure from a model card, community table, or vendor spec is marked
  as such. Never mix the two silently in one comparison.
- **Rank optimizations only after the roofline is measured.** Two rankings produced in this
  project were reversed by measurement (the FWHT looked like the top target until its
  traffic was computed, then measured at ~2% of a token). State hypotheses as hypotheses.
- **A kernel change needs three things before it counts**: a roofline argument for why the
  time is there, an A/B against a source build of the same commit, and a correctness check
  that greedy output matches the pinned binary. A faster wrong kernel is worthless.
- **Record the machine state with the result.** Launch overhead measured 1.6 us idle and
  2.9 us under load; `scripts/bench.sh` prints `/proc/loadavg`. Any result without a quiet
  machine is provisional.
- **Keep patches rebasable.** Kernel edits carry a corresponding file in `patches/` plus a
  note naming the upstream commit they apply to, so the pinned checkout stays disposable.

## Architectural Boundaries

- `third_party/llama.cpp` is a pinned upstream checkout and is never the place a change
  lives. Every edit there has a matching patch under `patches/`; the checkout can be
  deleted and regenerated by `scripts/build.sh` at any time.
- Compute stays in llama.cpp. This repository owns configuration, measurement, patches, and
  serving; it does not vendor a second copy of ggml or fork the CUDA backend wholesale.
- The serving layer talks to `llama-server` over its OpenAI-compatible HTTP API only. No
  private C API, no linked `libllama`.
- Weights are never stored in the repository or in git history; `models/` is gitignored.

## Prohibitions

1. Do not run stock llama.cpp against these packings. `Q2_0` loads without a warning and
   produces garbage.
2. Do not state a speedup without an A/B on this card and a quoted `results/` file.
3. Do not commit model weights, CUDA binaries, or build outputs (`bin/`, `models/`, `out/`,
   `build/`, `third_party/` are gitignored).
4. Do not change the pinned fork commit without recording the old and new commit and
   re-running the baseline; every prior benchmark becomes uncomparable.
5. Do not treat a timing taken under `ncu` as a wall-clock number. Profiling inflates
   durations by 100-1000x and removes launch overhead.
6. Do not report a decode or prefill figure without the depth (`-d`) it was measured at.
   KV traffic is most of the difference between 0 and 32K depth.

## Git Conventions

Scoped Conventional Commits, so the evidence trail is greppable:

- `bench:` a measurement run or a results/ log commit
- `kern:` a CUDA kernel change (must carry a `bench:` commit for the A/B)
- `profile:` profiling harnesses or profiling results
- `docs:` including ADRs
- `chore:` setup, build, and acquisition scripts

Commit messages for measurements state the pack, the depth, and the delta, for example:
`bench: PQ2_0 pp512 498 t/s on sm_86 source build (baseline 0 t/s, first run)`.

## Session Handoff

Long-running workstreams use GitHub issues for cross-session continuity. See `docs/handoff-protocol.md` for the full protocol.

- Label: `session-handoff`
- One issue per workstream (not per session)
- On session start, read the relevant handoff issue and confirm the **Next action** with the user before executing.

## Common Development Rules

### TDD (Red → Green → Refactor)

All implementation work proceeds in this cycle:

1. **Red**: write a failing test that captures the intended behaviour.
2. **Green**: write the minimum code that makes the test pass.
3. **Refactor**: tidy up while keeping tests green.

When a test fails, fix the production code — do not delete, skip, or weaken the test.

### Measure, Don't Conjecture

Base decisions on observed data, not assumptions. Before optimising, claiming a bottleneck, or asserting that something is slow or broken, measure it — profile, benchmark, log, or reproduce. When you report a cause, cite the measurement that supports it.

### Git Conventions

- **Conventional Commits**: `feat:` `fix:` `docs:` `refactor:` `test:` `ci:` `chore:`. Project-specific prefixes (e.g. `data:`, `experiments:`) live in the project's `AGENTS.md`.
- **Branch naming**: use a short prefix for the agent or author followed by a topic, e.g. `claude/<topic>`, `codex/<topic>`, or `human/<topic>`.
- **Trailer**: when an AI agent authors the commit, append a trailer crediting the agent. Do not embed model name or session info in the trailer; put those in the commit body if needed.
- **Pre-push hook**: install via `cp git-hooks/pre-push .git/hooks/pre-push && chmod +x .git/hooks/pre-push` (or `git config core.hooksPath git-hooks`). The hook runs format / lint / clippy before every push. Tests are intentionally omitted — TDD keeps them green at commit time.

### Pull Requests

- **Always ready for review.** Open PRs in the "ready" state, never as drafts. Draft PRs do not fire review-requested events and slow the loop.
- **Auto-subscribe after creating a PR.** Immediately after the PR is created, subscribe to its activity without asking the user. Rationale: the user explicitly opted into the "agent opens and watches its own PRs" workflow at the template level, so the per-PR confirmation is noise. Unsubscribe only when the user says to stop, when the PR merges, or when it is closed unmerged.
- **One PR per workstream**, matching the handoff issue. Reference the issue with `Closes #N` per `.github/PULL_REQUEST_TEMPLATE.md`.

### Stream Idle Timeout Mitigation

Cloud agent sessions occasionally fail with `Stream idle timeout - partial response received` on long output. To reduce risk:

1. **Stage long writes.** For long documents or source files, write the skeleton (headings, function signatures, trait stubs) first, then fill each section in follow-up edits. Avoid single blocks larger than ~200 lines.
2. **Watch out after large reads.** Reading a big file (e.g. `Cargo.lock`, large generated modules) and then immediately producing long output is a common trigger. Split into separate turns or excerpt only the relevant portion.
3. **Recover carefully.** A timeout can still leave the file write completed. Run `git status` before retrying so the same content is not written twice.

### Common Prohibitions

1. Do not delete, skip, or comment out existing tests.
2. Do not modify CI configuration without explicit instruction.
3. Do not weaken production code merely to make tests pass.
4. Do not commit credentials, API keys, signed URLs, or anything in `.env*`.
